# AL-STYLE deployment

Publish the user's current project using the bundled client and the company gateway at `https://server.al-style.kz/platform`. It works in Codex and Claude Code. Install missing Git/Python automatically using the launchers below; the employee need not know Git or install developer tools beforehand. Employees need their own operator-issued invitation, not SSH or Coolify credentials.

The canonical skill source is `https://github.com/alstyle-vibecoding/al-style-deploy`. When the user asks to install or update **the skill itself**, follow [installation and updates](references/install.md), then read the updated entrypoint. Ordinary application deployments use the already installed skill.

## Prepare the computer

Start with the bundled launcher in the employee's local execution environment, before invoking Python or Git directly:

- macOS/Linux/WSL: `sh "<skill-directory>/scripts/run.sh" --setup-only`.
- Native Windows: `powershell.exe -NoProfile -File "<skill-directory>/scripts/run.ps1" -SetupOnly` (use `pwsh` if that is the available PowerShell).

The launchers verify working Git and Python 3.12+, reuse installed tools and install what is missing. Python is installed privately through a pinned, checksum-verified Astral uv release. Native Windows uses checksum-verified MinGit from Git for Windows in the same personal directory. They do not need a preinstalled Python, Git, Node or Docker. Read [setup details](references/setup.md) only for a setup failure or system prompt.

Run **all** client commands through the corresponding launcher: `sh "<skill-directory>/scripts/run.sh" inspect --path "<project>"`, or `powershell.exe -NoProfile -File "<skill-directory>/scripts/run.ps1" inspect --path "<project>"`. Replace `inspect` with `login`, `publish`, `status`, etc. This uses the selected runtime and private Git without restarting the agent or changing global PATH. Use `--help` for the client's commands.

If the OS requires employee confirmation or an administrator password, explain the specific system request and let the employee confirm it privately; never request the password in chat. On macOS exit 20 / `SETUP_PENDING` means Apple's Command Line Tools installer needs completion. Resume the same setup command after completion, then continue publishing. A Windows execution-policy error has an ordinary default-policy case covered in [setup details](references/setup.md); resolve that case instead of asking the employee to install Git/Python manually. Respect corporate installation restrictions and the agent's actual permissions; do not bypass them or report a pending installation as successful.

Never print credentials, read the client's session file into the conversation, put credentials in the project, or substitute a company-wide GitHub/Coolify token.

## First publication

After computer preparation and login, **ask the employee for the project's display name and desired address before the first publication**. Reuse answers already given. Read `me` for the live `domain_suffix`, and propose a concrete URL such as `https://catalog.<domain_suffix>`. The display name can be Russian; the short address uses Latin letters, digits and single hyphens. Ask both together, for example: “Как назвать проект и какой адрес выбрать? Например, «Каталог товаров» и catalog.<domain_suffix>”. Do not invent these choices or create/push a repository before the employee answers.

Check the answer with `domains --label <short-address-or-full-hostname>` through the launcher. If taken, ask for another address; never take over another project's route. A domain outside the suffix returned by `me` needs operator configuration and DNS: explain this and offer a currently supported address. Changing Coolify alone does not create DNS. The current pilot suffix is `89.126.193.220.sslip.io`; always use the live value rather than guessing a company wildcard. If the employee specifically requires an unavailable company domain, pause the publication for operator DNS setup instead of substituting a different address silently.

When `inspect` reports a saved project mapping, read `status` and reuse its name/address without asking again. This version keeps project identity fixed; requests to rename or move an existing domain require operator help. Preparing the deployment manifest or Dockerfiles can continue while waiting for the first name/address answer.

### Persistent records and uploaded files

Before first publication and before updating an existing project, read [persistent application data](references/persistence.md) and inspect actual record and upload writes. Convert file-based business records (SQLite/mutable JSON/CSV) to a managed PostgreSQL database with a project-specific, repeatable import; preserve an existing managed database. Put receipts, photos and other changing uploads in named volumes on the writing service. Stage existing local data privately with `stage-data`, exclude reviewed data paths via `.alstyle/storage.json`, and keep data out of Git and runtime image layers. Preserve IDs, balances, relationships and attachment paths. Complete authorized import and verify counts/hashes, then verify they survive a harmless new deployment. Do not declare deployment complete with an empty replacement database or volume. For an existing live app, export data before replacing its container; retain storage names/paths and do not overwrite newer server data from the local copy. A truly stateless app requires no invented database or uploads volume.

### Tests, resources and secrets before publication

Preserve the project's features, design and data. Add meaningful automated tests for its actual critical paths: startup/health, main user action, authentication/authorization if present, input errors, and any repaired bug. For a static page, test its build/output and navigation rather than adding a fictitious backend. Fix failures with the smallest necessary changes and run the affected tests again. Clean generated caches, unused temporary files and accidentally bundled dependencies; do not delete user assets, records, uploads or dependencies merely because they look unused. Avoid redesigns, framework migrations or broad refactors. After three unsuccessful repair/test cycles, report the concrete unresolved failure and stop publication instead of removing tests/features to make it pass.

For each service, prepare a named Dockerfile stage such as `tests` that actually runs these checks and exits nonzero on failure. Set `test_stage` to that stage's name in `.alstyle/deploy.json`. The company builder runs it before building/pushing production images, using synthetic test secrets and fixtures. Production credentials must never enter Docker build arguments, layers, fixtures or test logs. Final runtime images can omit test tools; a failed test stage blocks publication.

Read the live quotas from `me`. Choose conservative service/database budgets within both project and total limits. Keep HTTP body/upload sizes, pagination, caches, background jobs and concurrency bounded where applicable. Test the actual relevant boundary (for example oversized requests are rejected or a cache evicts entries), not just the numeric config constant. After deployment, recheck health/status and a few representative requests with bounded concurrency; investigate crashes, restart loops and available diagnostics, then make a focused fix. Never run unlimited stress tests on the shared server or increase quotas to hide a failure. Hard memory/CPU/process/log limits are enforced by the gateway; do not claim to have measured RAM when the employee diagnostics do not provide it.

Run the local secret scan **before reading potentially sensitive configuration into chat and before any push**. Remove real keys/passwords from source and replace their usages with environment lookups, preserving behavior. Process values locally without printing them or including them in tool arguments/messages. Existing `.env` values can be staged with `stage-env --path <project> --source <file> --names KEY1,KEY2 --move-source`; this writes a protected JSON file and a backup outside the project and prints names/paths only. Move only a real `.env` file belonging to this project. If it also contains needed nonsecret settings, preserve those in normal config or an example file before moving it. For hardcoded literals or complex dotenv syntax, use a small local script to extract the authorized values into a protected JSON file outside the project and replace those precise literals; do not read their contents into the conversation. Never use `eval` or execute an environment file.

Reference every imported name in its service's `secrets` list, then publish with `--secrets-file <private-JSON-path>`. The client transfers values to the encrypted gateway secret store **before pushing**, and the gateway supplies them to Coolify runtime ENV at deployment. They are not placed in Git or GitHub workflow inputs. For existing projects, the same flag updates ENV on the next publication; `secret-set` remains available for private interactive input. Scan again after refactoring and keep `.env.example` limited to explicit placeholders. If a real secret was already pushed previously, deleting it from the next snapshot does not revoke it or remove history: identify the affected credential privately, require rotation, and do not claim the leak has been undone or rewrite shared history without authorization.

1. Complete computer preparation above and identify the intended project directory. Run `inspect --path <project>` through the launcher to discover files, stack indicators, and the publication configuration. If not signed in, open an interactive terminal for the employee to run the launcher's `login` command and enter their invitation privately. Continue the deployment after successful login. A missing invitation or unconfigured organization requires an operator; do not fabricate an account or use another person's invitation.
2. Read the relevant project entrypoints and build configuration. Prepare working Dockerfiles for its actual technology, using a non-root numeric user and an HTTP port above 1023. Listen on `0.0.0.0`. Account for framework build output, migrations, native libraries, and writable directories. Read [the contract](references/contract.md) to configure multiple services, databases, volumes, environment and admin routes. For static sites, [the static Dockerfile](assets/static.Dockerfile) is a usable starting point.
3. Write `.alstyle/deploy.json` using the contract. Include a public health endpoint returning 2xx. Specify the admin route only if the application has a real admin interface. Implement administrator creation inside the application/container using its existing authentication system. Require first-login password replacement when the application supports it; never claim the gateway creates an admin account merely from an admin route.
4. Run appropriate local application checks with the tools already available, then `scan --path <project>`. Docker and the application language runtime are not prerequisites on the employee computer: builds run on GitHub. If local checks need unavailable tools, use the remote build and public/runtime checks to validate the actual result instead of blocking publication to install Docker or every app dependency. Resolve exposed credentials and unexpected files. Report affected filenames without secret contents. Database dumps, local databases, credentials and project-defined GitHub Actions workflows are excluded from publication; put required configuration in the gateway secret store. Do not upload sensitive history to work around a failed scan.
5. For a new project run `publish --path <project> --name <repository-slug> --title "<employee's display name>" --domain "<employee's chosen address>"` through the launcher. Derive a short lowercase slug from the agreed name; the title and address come from the employee. The gateway reserves the address atomically and saves the title in Coolify. It assigns the chosen hostname to the `web` service if public, otherwise the first public service; additional public services receive separate addresses. The client creates a private repository, commits a clean snapshot and requests the build/deploy. It maintains a separate publication checkout, preserving the user's existing Git remotes and history. The project mapping in `.alstyle/project.json` contains no secrets. Existing projects use `publish --path <project>` without changing their identity.
6. Run `status --path <project>` while deployment progresses. Use `wait --path <project>` for a bounded wait. Treat `healthy` as the gateway's confirmation of the deployed release and public HTTP checks. A successful push or accepted build is not a working application. Report the repository, actual application URL, admin URL if present, and deployment result.

## Updates and recovery

Publish the same project again after changes; the existing repository is reused. Concurrent deployment requests are rejected. Repeat requests for the same commit/configuration reuse the durable job.

For runtime secrets, the user runs `secret-set --path <project> --name KEY` and enters a value privately. The agent can use `--stdin` with an existing authorized secret source without printing it. The manifest refers to secret names only. Missing required secrets are actionable configuration errors.

Use `history --path <project>` to find successful releases, then `rollback --path <project> --release <id>` when the user asks to undo a release. Rollback restores application images/configuration; database migrations and persisted data require their own recovery procedure. Do not describe an image rollback as a database restore.

If publication fails, use `logs --path <project> --kind build` or `logs --path <project> --service <name>` to inspect the employee's own diagnostics, repair the concrete project/configuration error and publish a new commit. Authorization failures, operator connection requirements, quotas or an unresolved provider outage require operator help. Do not switch to personal repositories, shared credentials, arbitrary SSH commands or direct Coolify access to bypass them.

## Issue employee invitations

When Danil or Nikita asks to give an employee deployment access, use the current operator's own gateway login and check `me`. Only accounts with `can_invite: true` can issue invitations. If not signed in, follow the normal private login procedure; a Coolify login does not automatically sign in this client. Ask for the employee's email and name only if missing, then run `invite --email <employee-email> --name "<employee-name>"` through the same launcher. This action needs no project or GitHub account.

The client saves the one-time invitation in a protected file outside the current project and prints only the recipient, expiry timestamp and file path. Link that local file for the operator to send directly to the intended employee; never read its contents into chat, publish it in a group, or send it elsewhere without explicit authorization. The invitation lasts 24 hours and is used once at login. New employees cannot issue invitations or access another employee's projects. The invitation endpoint cannot grant operator rights, recover an operator account or reactivate a disabled account; those tasks require the server operator.
